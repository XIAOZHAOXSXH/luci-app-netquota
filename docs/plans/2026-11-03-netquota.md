# NetQuota implementation plan

**Goal:** Build and install a native LuCI account and shared monthly quota application, using the connected GL-MT3000 for development and reserving GL-MT6000 certification for its actual firmware.

**Architecture:** Lua 5.1 and SQLite provide persistent accounts, calendar periods and authentication. An independent nftables inet table enforces one named quota per account for all authenticated IPv4 clients and both directions. LuCI uses an rpcd executable plugin with narrow ACLs. A separate local HTTPS portal has cookie sessions and no administrator RPC access. Existing fw3 filtering continues to apply.

**Tech stack:** Existing Lua, lsqlite3, nixio, luci.jsonc, uci, uhttpd, nftables 0.9.6, procd; Python only for workstation packaging/test/deploy tools. Source packages: `netquota/` and `luci-app-netquota/`.

## Design decisions

1. Verify named quota/counter creation on the router before network implementation. Never flush global rules. Use `inet netquota` and a separate fail-closed guard owned by this application.
2. Prefer a self-contained local portal if openNDS 9 cannot be safely sourced and validated. openNDS 10 requires OpenWrt >=22.03; it cannot be assumed compatible with this 21.02 vendor build. Any change is documented explicitly. Account quota enforcement remains independent of the portal implementation.
3. Default installation does not capture br-lan. Enable only an explicitly selected guest interface and egress devices. Refuse management/WAN/loopback capture, missing TLS or enabled acceleration. Preserve existing network settings. No automatic SSID/WAN/DHCP rewrites.
4. IPv6 forwarding from/to the selected network is blocked for this first implementation. Unknown IPv4 clients are blocked. Only selected egress devices are permitted, preventing alternate routed/VPN exits. Router input is limited to DNS, DHCP and portal; ordinary users cannot access SSH/LuCI.
5. A single quota is referenced by upload/download rules for all sessions of an account. Named direction counters record bytes. Gate forwarding during checkpoint-and-rebuild mutations; initialize counters/quota from persistent usage. Never rebuild from a stale database while live traffic can pass.
6. Calendar reset days remain anchored at 1-31 with short-month clamping. Settings/account changes take effect at the current period end without clearing usage. Epoch timestamps persist; timezone changes are validated and must not reopen settled periods. Revoke network sessions on rollover/password change/delete.
7. Password hashing uses an existing verified native crypto interface with strong configurable cost and unique CSPRNG salt. No credentials in command arguments, logs or temporary files. Portal requires HTTPS, unpredictable HttpOnly/SameSite/Secure cookie sessions, CSRF, rate limiting and server-side identity. Quota-exhausted users retain portal access.

## API contract

Admin rpcd object `netquota`: `status`, `get_summary`, `list_accounts`, `get_account`, `create_account`, `update_account`, `delete_account`, `get_traffic`, `get_settings`, `update_settings`, `get_portal_info`.

Responses are `{ok:true,data:...}` or `{ok:false,error:{code,message}}`. `list_accounts`/`get_traffic` data: `{items:[...],updated_at}`. Each account has `id`, `username`, `quota_bytes`, `reset_day` (null means inherit), `effective_reset_day`, `pending_reset_day`, `pending_effective_at`, `period_start_at`, `period_end_at`, `next_reset_at`, `upload_bytes`, `download_bytes`, `total_bytes`, `remaining_bytes`, `usage_percent`, `online`, `session_count`, `exhausted`, `created_at`. Admin writes never accept passwords back in responses. `get_settings` data contains `default_reset_day` and `timezone`. Settle changes next period.

Portal methods are never exposed by admin rpcd ACL. Portal identity is derived from its session token. Input username is 3-24 ASCII letters/digits/_/-, case insensitive; passwords 8-128 bytes; positive integer quotas <=2^53-1; all IDs and numbers validated strictly.

## Implementation tasks and verification

1. `docs/compatibility/`: router read-only inventory, isolated kernel quota probe, capture offload/portal/TLS constraints. Verify named object references and text parsing because nft JSON support is absent.
2. `netquota/files/usr/lib/lua/netquota/`: database/schema, calendar periods, crypto, validation and account service. Meaningful tests for 31st/leap year, staged changes, rollback, hash verification, account isolation and input injection.
3. Same backend plus `netquota/files/usr/sbin/netquota`, rpcd adapter, init/UCI: guard, named quotas, sessions, persistence, procd, executable rpcd. Verify actual router Lua load, SQLite CRUD and ubus with no network capture.
4. Separate portal resources and handler: HTTPS-only credential POST, auth/CSRF/expiry/rate limiting, IP/MAC association via server neighbour data, self password changes and revocation. Verify authentication domain isolation and rejection cases.
5. `luci-app-netquota/`: six native views, shared RPC helpers and scoped CSS using the prototype's restrained blue/white cards. Backend data only, explicit errors and empty states, mobile table scrolling. Verify LuCI rendering and account interactions.
6. `tools/`: deterministic IPK packaging, safe SSH deployment (password from environment), preflight and backup/restore. Install separate packages with disabled network capture; verify rpcd/menu/procd on MT3000.
7. Routed isolated test network only: concurrent clients share quota, direction counters, exhaustion stops established flow, another account unaffected, IPv6 blocked, service restart preserves usage, firewall reload does not bypass. Clean up temporary topology. Record actual outcomes and untested conditions.
8. README, operating guide and test report: installation/upgrade/uninstall/data retention, TLS trust setup, guest selection, acceleration tradeoff, MT6000 preflight, current limitations. No 24-hour or MT6000 certification claims without those tests.
