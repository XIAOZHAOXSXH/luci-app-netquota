# MT3000 共享配额验证与旧结论纠正

2026-11-03，GL-MT3000 原厂 4.11.0，OpenWrt 21.02-SNAPSHOT，kernel 5.4.211，nftables-nojson 0.9.6。

旧版本文及旧 P0 脚本验证的是「每方向各一份额度」，不能证明账号共享总额度。该结论已撤回，脚本已由直接调用生产规则生成器的测试替换，旧记录保留在 Git 历史中。

## 正确计量模型

一个账号只有一个 `quota q_<period_id>`，其所有终端的上传、下载规则引用同一对象。一次请求和一次响应是两份实际经过路由器的 IP 流量，两者均应扣量。

规则使用 `until` 配合 `accept`，之后为受控接口的双向兜底 `drop`。方向 counter 放在 quota 后面，仅记录获准通过配额检查的报文；被丢弃的重复尝试不再收费。quota 自身的 used 值包含触发阈值的内核报文，可能略高于已放行方向计数的和；后台保留其耗尽状态，剩余额度为零，不会因为重新登录或重建规则再获额度。

`nft -nn list` 会省略默认的 `until` 关键字，解析器同时接受裸额度和 `until`，拒绝反向的 `over`。`nft -j` 不可用，`nft -f -` 因缺少 `/dev/stdin` 不能使用。规则通过私有临时文件校验和原子提交。

此固件没有 nft NAT chain 模块。HTTP 捕获使用自有 iptables `NQ_CAPTIVE` 链；计量与拦截使用独立 nft `inet netquota` 表。nft 的 accept 仍需通过原有 fw3 规则，不替代其网络隔离策略。

## 实测

测试由 `tests/router-lab.sh` 创建独立桥和三台网络命名空间客户端，另有一台服务器，均不接入现有 LAN/WAN/Wi-Fi。

| 项目 | 结果 |
|---|---|
| 同账号两终端分别传输四个 1000B ICMP payload 请求/回复 | 上传 4112B，下载 4112B，共享 quota 恰为 8224B |
| 无后台轮询时耗尽 16000B 额度 | 两个终端均被内核阻断 |
| 耗尽后继续发送 | 已放行上传/下载计数不增长 |
| 另一账号通信 | 继续通过 |
| 未认证 IP、冒用认证 IP 但 MAC 不符 | 不通过认证规则 |
| IPv6 基线能通，装规则后再测 | 被明确阻断 |
| 守卫下重建规则 | 方向计数与耗尽状态保持 |

另用真实 procd/rpcd/uhttpd/SQLite 验证：受信任测试证书的 HTTPS 登录、三个客户端认证、50GB 的 64 位 RPC 额度、后台落盘、跨终端断网、耗尽后改密、缺 CSRF 的真实 HTTP 403，以及服务重启恢复均通过。见 `tests/test_portal_router.sh`。

## HNAT 的实际影响

HNAT 开启时，隔离桥上的基础转发也会失败；临时写入设备原有 `hook_toggle=0` 后，IPv4/IPv6 基线和生产接口/MAC 匹配均正常。因此旧版「接口匹配不可靠」「应去掉 MAC 绑定」的推论无效。测试已恢复原 HNAT 配置及运行开关。正常使用要求关闭加速并核查真实业务链路。

## 复现

在已安装本项目、网络接管关闭、配置无未提交改动的测试设备上执行：

```powershell
python tools/test_on_router.py --fingerprint <设备SSH指纹> --network --temporary-disable-hnat
```

密码由环境变量或交互输入提供。工作站只上传源码到 `/tmp`，基础测试不安装包。原生门户端到端测试需要已安装修正版，并在上述隔离拓扑保留期间执行 `tests/test_portal_router.sh`；该脚本备份、暂改并恢复 NetQuota 配置和 HNAT，不修改 LAN/WAN/Wi-Fi。

以上证明 MT3000 的隔离有线软件转发链路。未据此宣称 MT6000、真实 Wi-Fi、全吞吐、突然断电及 24 小时稳定性通过。
