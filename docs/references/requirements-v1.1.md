## 0. 给开发 Agent 的执行说明

请先阅读本文件，再完整查看同目录中的 `luci-app-netquota-prototype.html`。目标不是把 HTML 作为独立网站部署，也不是通过 iframe 嵌入 LuCI，而是将其视觉与交互转化为原生 LuCI 页面。

开发时必须遵守以下原则：

1. `luci-app-netquota` 是 LuCI 前端应用，使用 OpenWrt 原生 LuCI 菜单、页面框架、登录会话和 RPC/ubus 通信。
2. 账号认证、流量累计、月度配额、自定义结算周期、超额断网和用户自助改密必须由路由器本地后端服务完成。关闭浏览器或退出 LuCI 后，后端仍须继续工作。
3. openNDS 负责 Captive Portal/客户端认证放行；NetQuota 负责账号身份、账号级月度流量账本及策略；由目标固件验证可用的 nftables 或 iptables/netfilter 机制负责账号级流量计量/配额拦截。不能把 openNDS 单客户端配额直接当成账号月度总配额。
4. 当前原型说明“多个终端使用同一账号时，共用该账号额度”。正式实现必须验证多终端共享同一配额对象，不允许简单地给每个终端都分配一份完整额度。
5. 不得擅自修改客户现有 LAN/WAN、Wi-Fi、VLAN、DHCP 或整个防火墙规则。必须明确选择受控网络接口/网络区域，并保护路由器管理网络。
6. 基础版不得偷偷加入完整版功能；也不得把尚未实现的功能展示为可用。
7. 在大量编写 UI 之前，先完成“MT6000 原厂固件环境探测 + openNDS 认证链路验证 + 加速旁路测试 + 账号共享总流量配额验证”四个技术验证门槛。

若目标设备不支持本文推荐的 nftables 账号级共享配额方案，先提交技术差异和安全可行的替代方案，不得静默退化为“每台设备各算各的”或“上传/下载各有一份额度”。

## 1. 项目目标与交付定位

NetQuota 是安装在 OpenWrt 路由器本地的一套多用户上网管理插件。管理员通过路由器现有 LuCI 后台创建上网账号、设置每个账号的月度流量额度，并查看当前周期流量使用情况。用户连接指定 Wi-Fi/受控网络后，通过 Captive Portal 登录；认证成功后才能访问互联网。账号当前结算周期内上传与下载总流量达到额度后，系统自动阻止该账号继续联网；在该账号配置的下一次月度结算日自动进入新周期。

### 1.1 核心价值

- 一人一个上网账号，账号之间流量独立核算。
- 每个账号有独立月度流量额度。
- 上传流量与下载流量合计计入月额度。
- 达到额度自动断网，每次账号结算日自动恢复。
- 管理员在 LuCI 内完成账号增删改、密码修改和流量查看。
- 全部服务和数据在路由器本地运行，不需要云服务器或月租服务。

### 1.2 基础版范围（本项目必须完成）

| 模块 | 基础版要求 | 说明 |
|---|---|---|
| 多账号管理 | 创建、删除、修改密码、修改月额度 | 用户名唯一；后端校验不能只依赖前端 |
| 用户认证 | 连接受控 Wi-Fi 后进入认证页，账号密码登录 | 认证页与 LuCI 管理后台分离 |
| 用户自助密码修改 | 登录门户的账号本人可凭旧密码更改密码 | 与管理员 LuCI 隔离；不能修改他人密码或流量 |
| 自定义重置日 | 系统默认重置日及每账号独立覆盖（1–31 日） | 变更从下个周期生效；短月取最后一天 |
| 月度流量配额 | 每账号独立设置额度 | 每账号独立结算周期；系统默认每月 1 日，可自定义每月 1–31 日 |
| 流量统计 | 单独统计上行、下行，合计扣减总额度；显示已用/剩余/周期 | 方向归属必须准确；基础展示、不含独立限速 |
| 自动断网 | 账号总流量达到月额度后自动撤销其在线会话并阻止继续联网 | 后端自动完成，不依赖管理员打开页面 |
| 自动恢复 | 到达每账号下次重置日期建立新流量周期，额度自动恢复 | 31 日遇短月取最后一天；账本不可覆盖 |
| LuCI 管理界面 | 集成在路由器现有 LuCI 中 | 不单独启动一个管理网站 |
| 本地持久化 | 路由器重启后账号和流量记录保留 | 使用持久化存储，不放在 `/tmp` |
| 部署交付 | 指定设备安装调试和图文说明 | 仅对确认过的设备/固件承诺兼容 |

### 1.3 明确不包含的功能（完整版或后续增值）

- 每个账号单独设置上传速度、下载速度上限。
- 实时上行/下行速度曲线、秒级实时速率看板。
- 管理员手动一键暂停/恢复单个账号的操作按钮。
- 多月历史报表、流量趋势图、CSV 导出。
- 多路由器集中管理、云端账号同步、远程 SaaS 管理。
- 短信验证码、微信登录、第三方身份认证、访客二维码。
- 复杂的设备黑白名单、设备数量限制、反共享账号风控。

说明：自动超额断网属于基础版必需功能；“管理员主动点击一键断网/恢复”属于报价单完整版功能，不应混淆。

## 2. 用户角色与典型流程

### 2.1 管理员

管理员使用 OpenWrt 原有管理员账号登录路由器 LuCI，不另设一套 NetQuota 管理员账号。进入“服务 → NetQuota 流量管理”后，可以：

1. 查看账号总数、在线账号数、额度用尽账号数和本月总用量。
2. 新建用户，填写用户名、密码和月流量额度。
3. 修改用户密码或月流量额度。
4. 删除账号；若该账号在线，后端先撤销它的所有认证会话。
5. 查看每个账号的上传、下载、合计、剩余和配额使用比例。

### 2.2 普通上网用户

1. 连接管理员指定的 Wi-Fi/受控网络。
2. 设备弹出 Captive Portal；若操作系统没有自动弹出，用户打开普通 HTTP 网页触发认证跳转。
3. 输入管理员分配的账号密码。
4. 后端验证账号存在、密码正确、当月仍有剩余额度。
5. 认证成功后 openNDS 放行该终端，并建立“账号—终端会话—IP/MAC”关联。
6. 流量按账号累计，不因断线、换 IP 或重新登录而清零。
7. 达到额度后，该账号所有在线终端被撤销认证；当月再次登录仍提示流量已用尽。
8. 该账号配置的下个结算周期开始后，账号恢复可登录状态。
9. 登录后的用户可进入“我的账号 → 修改密码”，验证原密码并设置新密码；不得接触路由器 LuCI 管理权限。

### 2.3 同账号多终端策略

**本方案按原型中的产品设定：允许同一账号多个终端同时在线，所有终端共用同一个账号月度总额度。** 例如用户手机和笔记本同时登录，手机用了 2GB、笔记本用了 3GB，则账号已用总量为 5GB，而不是每个终端各有一份额度。

这是本项目最重要的技术验证项。实现时必须将同一账号所有活跃终端的双向转发流量计入同一个账号级 quota/counter；达到额度时撤销该账号全部会话。不能用“每个终端分别配置同样的 50GB”代替共享额度。

如果目标固件的内核/nftables 不能实现同一命名 quota 对象被多个客户端地址规则共享，Agent 必须暂停该功能开发并报告原因，不能暗中改为单终端模式。单终端模式只有在项目负责人明确同意修改产品范围后才可采用。

## 3. 总体技术架构

```text
普通用户终端（手机 / 电脑 / 平板）
        │ 连接受控 Wi-Fi
        ▼
openNDS Captive Portal  ─── 登录表单 / FAS Token ───► NetQuota 本地认证服务
        ▲                                                 │
        │ 认证放行 / 撤销会话                              ├──► SQLite 本地数据库
        │                                                 │
        └────────────── NetQuota 后台守护进程 ◄───────────┘
                              │
                              ├──► 经实机验证的流量计量/拦截规则 ───► WAN / Internet
                              │
LuCI 管理页面 ── RPC / ubus ──► NetQuota RPC 接口 ──► 数据库 / 后端服务
```

### 3.1 组件职责

| 组件 | 职责 | 不应承担的职责 |
|---|---|---|
| LuCI / `luci-app-netquota` | 页面、菜单、表单、状态展示、RPC 调用 | 不直接解析内核规则，不自行计算最终流量，不承担守护进程工作 |
| `netquota` 后端服务 | 账号、密码校验、数据库、周期切换、会话映射、策略协调 | 不依赖浏览器保持在线 |
| 本地 FAS/认证页 | 普通用户登录、验证凭据、处理 openNDS 安全认证流程 | 不提供路由器管理员功能 |
| openNDS | Captive Portal、认证终端会话管理、客户端认证/撤销 | 不单独作为账号级月度总流量数据库 |
| netfilter/nftables 或固件兼容后端 | 对受控网络账号关联 IP 做上行、下行分别计量，共享总额度拦截 | 最终机制必须由 MT6000 原厂固件实机验证，禁止直接推断可用 |
| SQLite | 持久化账号、月度账本、会话映射、系统状态 | 不把明文密码存入数据库 |

### 3.2 前后端边界

管理页面通过 LuCI 的 RPC/ubus 访问后端。所有敏感业务操作必须在后端进行权限检查、输入验证和事务处理。前端隐藏按钮不等于权限控制。

浏览器关闭、LuCI 退出、管理员电脑断网时，后端仍须持续执行：流量核算、超额检测、会话撤销、按账号结算日切换和数据持久化。

## 4. 认证与网络控制设计

### 4.1 推荐组件：openNDS

优先验证并采用 openNDS 当前稳定文档所描述的 FAS（Forward Authentication Service）与 BinAuth 扩展机制：

- Captive Portal 由 openNDS 控制受控网络客户端的预认证/认证状态。
- FAS 接收登录表单提交，调用 NetQuota 后端验证用户名和密码。
- 认证通过后，按 openNDS 规定的安全 Token/Hash 流程将认证结果交还 openNDS。
- BinAuth 或等效会话回调记录认证成功、会话结束、主动撤销等事件。
- 使用 `ndsctl` 查询客户端 JSON、查看状态、认证或撤销指定 IP/MAC；不得在前端直接执行 shell 命令。

不要自己猜测 FAS 参数、Hash 生成方法或 openNDS 命令参数。必须按目标设备实际安装的 openNDS 版本文档和 `ndsctl -h` 验证。

### 4.2 登录校验逻辑

提交登录时，后端按以下顺序判断：

1. 用户名是否存在且账号未删除。
2. 密码是否通过安全哈希校验。
3. 当前月份的账号累计使用量是否小于月额度。
4. openNDS 客户端是否为合法的受控网络终端。
5. 写入会话记录，完成 IP/MAC 与账号 ID 的映射。
6. 创建或更新该账号的 nftables 客户端地址关联。
7. 按 openNDS FAS 规范完成认证放行。

若任一步骤失败，必须拒绝联网并返回普通用户可理解的提示，不得因为 RPC/数据库错误而直接放行。

### 4.3 账号级流量计量与超额断网（关键设计）

**统计口径：当月上传字节数 + 当月下载字节数。** 只统计通过路由器受控网络转发到互联网的流量；不应把 LuCI 管理流量、路由器自身访问互联网的流量、同一 LAN 内部互访流量混入账号配额。

推荐技术路线：在受控网络的转发路径建立 NetQuota 自有 nftables 规则和账号级命名 quota 对象。每个账号一个逻辑 quota 对象；该账号所有已认证终端当前使用的 IPv4 地址（以及经验证支持的 IPv6 地址）均关联到同一对象。上行匹配客户端源地址，下行匹配客户端目的地址；双向流量共同消耗该账号同一个额度对象。

实现时需验证：

- 目标内核、nftables 用户态和所需内核模块支持命名 quota 对象。
- 同一个命名 quota 对象可由多个规则引用，并确实累计为同一个总字节数。
- 上行和下行两组规则确实共同消耗一个 quota，而不是分别给额度。
- IPv4/IPv6、NAT 回程、DHCP 地址更新、多个客户端 IP 均被正确归属。
- 当 quota 到达上限时规则能在转发路径拦截后续流量，并由后台撤销该账号全部 openNDS 会话。
- 规则挂载位置与 openNDS、fw4 规则优先级兼容；防止预认证流量被误计。

建议用独立 NetQuota nftables table/chain 或 fw4 支持的 nftables include 机制集成，不直接重写 OpenWrt 的主防火墙规则，不 flush 整张防火墙表。规则只作用于指定受控网络到 WAN 的转发流量。

**流量配额不应仅依赖 openNDS 的 `uploadquota` 和 `downloadquota`。** openNDS 原生按客户端提供独立的上传/下载 volume quota 与 rate quota；这不能自动表达“同一账号下多台终端的上传+下载共享一个总额度”。openNDS 可用于客户端会话管理和认证撤销，账号级总量应由 NetQuota 账本/共享 quota 实现。

### 4.4 Flow Offloading 注意事项

软件/硬件 Flow Offloading 可能让已卸载连接绕过后续传统转发规则。若计量/配额链无法看到这些数据包，流量会少计，甚至突破额度。

首版默认策略：对受控网络的计量/配额路径关闭或排除会绕过规则的 flow offloading；若目标固件能够证明其 flowtable 计数与配额拦截链兼容，则可以采用经测试的优化方案。不得为了性能默认打开 offloading 而不验证配额准确性。

关闭 offloading 可能降低路由吞吐量，必须在实际设备上做 iperf/真实下载测试，并在交付说明中记录性能影响。

### 4.5 IPv6 与网络旁路

首版必须明确 IPv6 策略。若 IPv6 尚未实现同等的账号关联计量与配额拦截，则受控网络不能保留绕过认证的 IPv6 WAN 出口；应在受控网络上禁用/阻断 IPv6 外网转发，直到 IPv6 计量通过验收。禁止只管理 IPv4、却让客户端从 IPv6 直接访问互联网。

用户流量必须经过安装 NetQuota 的路由器。若 AP、交换机、旁路网关、第二 WAN 或 VPN 路由使用户流量绕过 NetQuota，系统无法保证配额准确。交付前需要核实拓扑。

### 4.6 网络隔离与管理面保护

- 强烈建议使用独立 Guest SSID/VLAN/接口作为受控网络，管理 LAN 单独保留。
- 不能未经确认就把 openNDS 直接挂到整个 `br-lan`。
- 必须确保路由器管理 IP、LuCI、SSH、DHCP、DNS 等基础服务不会被认证规则锁死。
- 将管理员维护终端/管理网段排除在 Captive Portal 和用户配额之外。
- 首次启用前做网络连通性检查；应用规则失败时不得破坏现有 WAN/LAN 基础连接。

### 4.7 认证页与密码传输

普通用户认证页与 LuCI 管理后台是两个不同入口。认证页不显示路由器管理员登录状态，也不允许访问账号管理 RPC。

登录凭据必须通过安全传输。优先使用可被客户端信任的 HTTPS 证书和本地 FAS 域名；若目标客户环境只能使用 HTTP 或不受信任的自签名证书，需在交付前明确说明该限制及风险，不得宣称登录过程具备端到端 TLS 保护。密码仅通过 POST 请求提交，不放在 URL、查询字符串或日志中。

## 5. 流量计量、单位和月度周期

### 5.1 单位约定

统一采用十进制流量单位：

- `1 KB = 1,000 bytes`
- `1 MB = 1,000,000 bytes`
- `1 GB = 1,000,000,000 bytes`

数据库始终保存整数 bytes，前端只负责格式化。不要在数据库中用浮点数保存 GB，以免累计误差。UI 展示最多保留 2 位小数。

### 5.2 账号用量公式

```text
本月总用量 bytes = 本月上传 bytes + 本月下载 bytes
剩余 bytes = max(0, 月度额度 bytes - 本月总用量 bytes)
使用比例 = 本月总用量 bytes / 月度额度 bytes * 100%
```

月额度必须大于 0。达到或超过额度即进入“流量用尽”状态。

### 5.3 可自定义的月度结算周期（客户新增，强制要求）

- 全局配置 `default_reset_day`，整数 1–31，默认 1。每个用户允许设置 `reset_day` 覆盖值；空值表示继承全局默认日。
- 重置日是**每个日历月的第 N 日、路由器指定本地时区 00:00**，不是间隔固定 30 天，也不是按账号创建日计算天数。
- 对不存在第 N 日的短月，采用 `min(N, 当月最后一天)`；保持固定的原始 N 值作为锚点，不将 31 自动永久改成 28。
- 示例：重置日 15：11/15 00:00 → 12/15 00:00；重置日 31：1/31 → 2/28（闰年 2/29）→ 3/31，避免日号漂移。
- 周期使用半开区间 `[period_start_at, period_end_at)`，所有读写使用 UTC epoch 时间戳持久化，界面使用配置时区显示；`period_start_at` 必须作为账本唯一标识的一部分，不能只用 `YYYY-MM`。
- 开始边界归新周期；跨界的一条持续传输必须按计量采样点和内核计数差额正确归属，并记录误差上限。跨期时强制中止旧会话并重新认证是优先的可测试策略；如做无感授权，必须证明数据不丢、不重计。
- 管理员修改重置日时保存为 `pending_reset_day`，**默认在当前周期结束后生效**；应展示生效时间，不能立即把已用流量清零。明确的手动“立即重置”不属于此次基础变更。
- 全局默认日变更对继承默认值的账号也采用“下个周期生效”，单独覆盖账号不受影响。
- 无可信时间/NTP 未同步、时钟回拨、时区突变时，不得重复开新账本或越权恢复；周期切换数据库事务/内核规则更新须可重入、幂等，并提供失败恢复/告警。
- 不做人工清零旧统计；每个周期生成新账本并保留旧记录以供审计。账号列表与流量统计页必须显示“本周期开始/结束/下次重置时间”，不能统一标注“本月 1 日重置”。

### 5.4 持久化与异常恢复

- SQLite 数据库放在持久化 overlay 存储目录，例如 `/etc/netquota/netquota.db`；严禁放在 `/tmp` 或其他重启丢失目录。
- 使用事务和 WAL/合适的同步策略，数据库定期 checkpoint。
- nftables 命名 quota 的当前用量/剩余值必须能够从数据库恢复；守护进程启动时先恢复账号、会话和 quota 状态，再开放新会话。
- 正常重启前应同步并保存最终计数；异常断电的计量误差取决于最后一次持久化间隔。应尽可能缩短 checkpoint 间隔并实测，不得在未实现持久化机制的情况下声称“任何突然断电都绝对零丢失”。
- 如果内核 quota 对象重建，必须用数据库已保存的累计 bytes 初始化，不能重启后把当月流量当成 0。

### 5.5 统计刷新频率

- 后端配额执行由内核 nftables 规则即时拦截为主，守护进程负责更新状态和撤销 openNDS 会话。
- 后端状态轮询/持久化建议 3–5 秒一个周期，实际值需兼顾 CPU、存储写入和超额误差。
- LuCI 页面建议 15–30 秒刷新一次，或提供手动刷新；这是基础展示，不是实时速率看板。
- UI 显示“数据更新时间”，避免将轮询数据误称为毫秒级实时。

## 6. 数据库设计

建议使用 SQLite，所有表使用外键和索引。具体字段允许 Agent 优化，但不得丢失以下业务信息。

### 6.1 `users` 用户表

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER/UUID | 主键，稳定内部 ID |
| `username` | TEXT | 唯一用户名，建议大小写不敏感唯一索引 |
| `password_hash` | TEXT | 安全密码哈希，不得存明文 |
| `quota_bytes` | INTEGER | 月度总流量额度，单位 bytes |
| `reset_day` | INTEGER/NULL | 1–31；NULL 继承系统默认重置日 |
| `pending_reset_day` | INTEGER/NULL | 下个周期待生效的重置日（含继承标记可另行建模） |
| `reset_day_effective_at` | INTEGER/NULL | 已排期的新重置日生效时刻 |
| `enabled` | INTEGER | 后端账号是否可登录；基础版 UI 不一定展示手动停用 |
| `created_at` | INTEGER | 创建时间 Unix 时间戳 |
| `updated_at` | INTEGER | 修改时间 |
| `deleted_at` | INTEGER/NULL | 软删除时间或 NULL |

### 6.2 `usage_periods` 账号结算周期账本（取代旧版 `usage_monthly`）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK | 周期记录 ID |
| `user_id` | FK | 用户 ID |
| `period_start_at` | INTEGER | UTC Unix epoch；实际起始时刻 |
| `period_end_at` | INTEGER | UTC Unix epoch；实际结束时刻（不包含） |
| `reset_day_applied` | INTEGER | 本周期固定的重置日策略快照 |
| `upload_bytes` | INTEGER | 当前周期上行流量，按用户→互联网定义 |
| `download_bytes` | INTEGER | 当前周期下行流量，按互联网→用户定义 |
| `total_bytes` | INTEGER | 必须 = `upload_bytes + download_bytes`，可以计算列/读取时推导 |
| `kernel_quota_used_bytes` | INTEGER | 内核配额恢复检查点，防重计/漏计 |
| `updated_at` | INTEGER | 最后一次可靠计数提交时间 |
| `closed_at` | INTEGER/NULL | 已结算关闭时间 |

唯一约束 `(user_id, period_start_at)`，并强制同一 user 的多个周期区间不得重叠。所有 up/down 计数按一次方向定义累计，处理 NAT/conntrack/forward hook 前后，防止同一包被双计。特别强调账户共享总配额的阻断是根据上传与下载之和，而**不是**给上传和下载各发一份完整额度。

迁移旧版 `YYYY-MM` 账本时需保留记录与实际开始时间的对应；无可靠数据时必须显式报告不可无损迁移，不能偷偷归零。

### 6.3 `sessions` 在线会话表

| 字段 | 类型 | 说明 |
|---|---|---|
| `session_id` | TEXT | openNDS 会话/token 标识（按实际版本适配） |
| `user_id` | FK | 关联账号 |
| `mac_address` | TEXT | 终端 MAC |
| `ipv4_address` | TEXT/NULL | 当前 IPv4 |
| `ipv6_addresses` | TEXT/JSON/NULL | 已识别 IPv6 地址集合（如首版支持） |
| `authenticated_at` | INTEGER | 登录时间 |
| `last_seen_at` | INTEGER | 最近活动时间 |
| `status` | TEXT | online / closed / revoked |

同一账号允许多条在线会话记录。MAC、IP 更新不能改变账号累计账本归属。

### 6.4 `system_state` 系统状态表

保存默认结算日、时区、当前有效策略版本、数据库 schema 版本、最近计数 checkpoint、最近成功同步时间、上次错误信息等。用于升级、恢复和诊断。

## 7. LuCI 页面与交互设计

### 7.1 页面集成原则

原型文件目前带有完整独立 sidebar 和 topbar。正式 LuCI 集成时：

- **删除原型独立的左侧 sidebar、顶部 topbar 和伪造管理员个人信息。** LuCI 已经提供这些框架。
- NetQuota 页面只渲染 LuCI 主内容区域。
- 通过 `menu.d` 注册菜单；通过 LuCI JavaScript view 路由承载页面；通过 rpcd ACL 授权自定义 ubus API。
- 使用当前 LuCI 主题的基础组件、表单、按钮、表格、提示信息；可保留原型的颜色、卡片、间距、进度条和图标风格，但不能破坏 LuCI 页面结构。
- 不使用 iframe，不在页面中启动独立管理 Web Server，不引用外部 CDN。
- 响应式适配桌面和手机浏览器；窄屏表格允许横向滚动。

### 7.2 菜单建议

```text
服务
└── NetQuota 流量管理
    ├── 总览
    ├── 账号管理
    ├── 流量统计
    ├── 结算设置
    ├── 认证页预览
    └── 系统信息
```

“认证页预览”用于展示普通用户看到的登录页样式/认证流程，不应混入管理员页面认证逻辑。若实际实现成本超出基础范围，可以保留静态预览，不做复杂主题自定义。

### 7.3 总览页

以 HTML 原型 `page-overview` 为视觉参考，至少展示：

- 总账号数。
- 在线账号数（按账号去重，不按终端数重复计数）。
- 流量用尽账号数。
- 当前各账号周期总用量。
- 账号用量排行（建议前 5 名）。
- 需要关注的账号（例如达到 80% 或以上）。
- 最近账号使用概况表：账号、已用/月额度、使用比例、状态、查看详情。

不能把“在线速率”或真实速率曲线放入基础版总览。若无数据，提供清晰空状态。

### 7.4 账号管理页

以 HTML 原型 `page-accounts` 为参考。

列表字段：

- 用户账号。
- 当前周期已用流量 / 月度额度 / 使用进度。
- 账号状态：在线、离线、流量用尽。
- 创建时间。
- 操作：查看详情、编辑、删除。

基本交互：

- 搜索用户名。
- 按状态筛选：全部、在线、离线、流量用尽。
- 按用户名或用量排序（分页可先做简单分页/全量小列表）。
- 新建账号弹窗：用户名、登录密码、月流量额度、每月重置日（默认继承全局设置）。
- 编辑账号弹窗：用户名只读；密码留空表示不修改；修改月额度及“下个周期生效的重置日”。
- 删除账号需二次确认；后端必须撤销该用户所有在线会话并删除/清理它的 nft 关联规则。

建议用户名规则：3–24 位英文字母、数字、下划线、短横线；用户名大小写不敏感唯一。密码最低长度应由后端统一校验，推荐至少 8 位；若为了沿用当前原型的 6 位下限，需由项目负责人确认并在 UI 与后端保持一致。密码哈希安全存储。

月额度预设建议：10GB、20GB、50GB、100GB、自定义。自定义必须是正数；后端将 GB 转换成整数 bytes 保存。

编辑额度时：
- 新额度低于当前已用量：立即进入超额状态，阻止继续联网并撤销所有在线会话。
- 新额度高于当前已用量：恢复可登录状态；不清空已用量。
- 修改密码：旧密码立即失效；不影响月流量账本。

### 7.5 流量统计页

以 HTML 原型 `page-traffic` 为参考。

展示各账号当前结算周期：

- 各账号上传流量。
- 各账号下载流量。
- 总使用流量。
- 周期额度。
- 账号有效重置日、当前周期日期范围与下次重置时间。
- 使用百分比。
- 按总使用量排序的柱状进度展示。

只提供当前周期数据；可在内部数据库保留历史月份，基础版 UI 不要求历史月份切换、导出和复杂图表。

### 7.6 认证页预览

以 HTML 原型 `page-portal` 为参考：简洁、清晰的 NetQuota 品牌、欢迎文案、账号输入框、密码输入框、登录按钮、认证说明。适配手机屏幕。

真实门户需显示明确状态：账号或密码错误、账号流量已用尽、认证成功、服务暂时不可用。门户还需提供“我的账号/修改密码”自助入口（已认证身份绑定，必须二次验证旧密码）。当账号额度用尽时，仍应允许访问门户内的自助改密页面，不允许借此访问互联网。不得在错误提示中泄露账号是否存在等不必要信息。

### 7.7 系统信息页

展示：

- NetQuota 版本。
- OpenWrt 版本、内核版本、架构。
- openNDS 版本和服务状态。
- NetQuota 后台服务状态。
- 数据库可读写状态。
- nftables 账号配额规则状态。
- 受控接口/网络区域（只读展示，除非有安全完整的配置流程）。
- 最近一次流量同步时间和错误告警。

这是排障信息，不扩展成完整网络配置中心。

### 7.8 页面视觉要求

以原型为视觉基准：浅灰蓝色页面背景、白色卡片、蓝色主操作按钮、圆角卡片、清晰的表格层级、绿色正常状态、橙色接近额度、红色额度用尽。信息密度适中，避免过度动画。

保持 LuCI 原生导航，不复制原型外层框架；在 LuCI 主内容区内使用标题、说明、卡片和表格。

## 8. LuCI RPC / ubus API 设计

建议定义一个自有 ubus 对象，例如 `netquota`，或使用清晰命名空间如 `luci.netquota`。具体注册方式按目标 rpcd/LuCI 版本实现。

建议方法清单：

| 方法 | 用途 | 权限 |
|---|---|---|
| `status` | 获取服务、openNDS、数据库、配额引擎状态 | read |
| `get_summary` | 获取总览卡片和排行数据 | read |
| `list_accounts` | 获取账号列表及当前月使用情况 | read |
| `get_account` | 获取单个账号详情 | read |
| `create_account` | 创建账号 | write |
| `update_account` | 修改密码/额度 | write |
| `delete_account` | 删除账号并撤销会话 | write |
| `get_traffic` | 获取当前月上传、下载、总量明细 | read |
| `get_portal_info` | 获取认证页展示信息/状态 | read |
| `get_settings` / `update_settings` | 读取/设置系统默认重置日与时区（仅管理员） | read / write |
| `get_my_account` / `change_my_password` | 用户查看本人周期与修改本人密码（单独认证域/会话） | user-self（严禁复用管理员 LuCI ACL） |

API 要求：

- 所有方法使用 JSON 请求/响应。
- 所有参数后端校验，类型、长度、数值范围和字符集严格验证。
- 所有写操作使用数据库事务；出错时回滚，不允许 DB 已更新但 nft/openNDS 状态未同步且无补偿记录。
- 返回一致结构，例如 `{ "ok": true, "data": {...} }`；失败时 `{ "ok": false, "error": { "code": "...", "message": "..." } }`。
- 不提供“执行任意 shell 命令”的 RPC。
- 删除、修改额度等敏感操作需在后端做幂等处理。
- ACL 只授予本插件确实需要的 ubus 对象与方法，不授予宽泛文件读写或任意 exec 权限。

## 9. 后端服务与进程管理

### 9.1 后台进程

- 使用 OpenWrt `procd` 管理服务，支持开机启动、崩溃重启、日志收集和状态查询。
- 不把流量统计任务放在 LuCI HTTP 请求中执行。
- 进程应有明确的启动顺序和依赖检查：数据库 → nftables 配额对象/规则 → openNDS 状态发现 → 会话恢复 → 接收新认证。
- 服务停止/卸载时只移除 NetQuota 自己创建的规则和资源，不得清空 fw4/openNDS 的其他规则。

### 9.2 建议目录结构

```text
luci-app-netquota/
├── Makefile
├── htdocs/luci-static/resources/view/netquota/
│   ├── overview.js
│   ├── accounts.js
│   ├── traffic.js
│   ├── portal.js
│   └── about.js
└── root/usr/share/
    ├── luci/menu.d/luci-app-netquota.json
    └── rpcd/acl.d/luci-app-netquota.json

netquota/
├── Makefile
├── files/etc/init.d/netquota
├── files/etc/config/netquota
├── files/etc/netquota/                 # 配置模板；运行数据库不可放进只读 package 文件
├── files/usr/sbin/netquota             # 主守护进程或启动入口
├── files/usr/libexec/netquota/         # FAS、BinAuth、RPC 辅助程序
└── files/usr/share/netquota/           # 静态认证页资源、默认模板
```

目录可以按最终语言/构建系统调整，但前端、后台、门户、配置、运行数据应保持职责分离。

### 9.3 技术栈选择原则

- LuCI 前端：优先使用 OpenWrt 官方 LuCI JavaScript view、`rpc` 模块和官方组件。
- RPC：通过 rpcd/ubus 暴露受 ACL 保护的业务 API。
- 服务管理：procd init script。
- 数据库：SQLite；若目标设备空间/依赖不满足，必须提交替代方案及数据完整性说明。
- 网络规则：跟随目标固件使用 fw4/nftables 或 fw3/iptables/厂商数据路径由实机探测决定；不可混用语法，不得假定原厂固件提供命名 quota 或所有依赖。
- 尽量使用系统已有组件，避免引入大型运行时、Python/Node 服务或外部依赖。
- 认证协议必须使用 openNDS 对应版本的官方 FAS/BinAuth 规范。

## 10. 安装、初始化、升级和卸载

### 10.1 安装前环境探测

安装脚本/部署步骤需要检查并输出：

- OpenWrt 发行版、版本、target、架构、内核版本。
- 包管理器（opkg 或 apk）和软件包 ABI。
- LuCI、rpcd、uhttpd 版本。
- openNDS 是否安装、版本、是否能启动。
- fw3/iptables 或 fw4/nftables 环境。
- 所需 nftables quota 表达式/内核模块是否可用。
- 存储空间、内存、系统时间/NTP。
- 计划管理的 LAN/Guest 接口、VLAN、WAN 区域及 IPv6 情况。
- 是否开启 software/hardware flow offloading。

### 10.2 初始化配置

部署时由实施人员指定受控网络接口/区域和管理网段豁免规则。没有明确目标网络时，不自动启用认证。初始化过程中备份相关配置文件，至少包括 `/etc/config/opennds`、`/etc/config/firewall` 及本方案实际修改的网络配置。

NetQuota 不得自动重置 Wi-Fi、DHCP、WAN、VLAN、桥接或交换机配置。

### 10.3 安装包拆分

建议拆分两个自研包：

- `netquota`：后台、认证服务、数据库初始化、procd 服务、nftables 管理。
- `luci-app-netquota`：LuCI 页面、菜单和 ACL。

openNDS 是外部依赖或单独系统包，不要把未验证的二进制硬编码进本项目。

### 10.4 升级

- 数据库 schema 带版本号，升级时执行幂等迁移。
- 升级前备份数据库和 NetQuota 配置。
- 升级中断后能够恢复或提示人工处理。
- package upgrade 不得覆盖用户数据库和自定义证书。
- 不得直接修改 openNDS `/usr/lib/opennds` 中会被软件包升级覆盖的示例文件；使用独立脚本路径并在配置中引用。

### 10.5 卸载

卸载时先停止 NetQuota 服务、撤销 NetQuota 认证会话、移除 NetQuota 自有 nftables 规则、移除自有服务和页面文件。不可执行 `nft flush ruleset`、`iptables -F` 或删除客户其他服务的配置。数据库默认保留或在显式确认后删除，具体按交付约定。

## 11. 兼容性与版本基线

### 11.1 版本策略

截至本文日期（2026-11-02），OpenWrt 官方下载页显示当前稳定系列为 25.12，最新服务版本为 25.12.6；25.12 已从传统 opkg 切换到 apk。官方发布说明还指出 24.10 系列预计于 2026 年 9 月结束支持。openNDS v10.0.0 及以上不支持低于 OpenWrt 22.03 的系统。

因此：

- **首个正式适配目标：GL.iNet GL-MT6000（Flint 2）原厂 GL.iNet 4.x 固件，按客户机器的精确固件版本/内核 ABI 构建。不得要求客户默认改刷原生 OpenWrt。**
- OpenWrt 25.12.x 与开源 mt76 分支仅作为第二阶段的其他固件适配，不作为原厂 MT6000 首发交付基线。
- 可将 OpenWrt 24.10.x 作为历史设备的兼容目标，但截至本文日期已过其预计 EOL 时间，需单独评估安全风险。
- 不建议在报价/宣传中继续无条件承诺 OpenWrt 21.02+。21.02 已停止维护，且 openNDS v10 不支持 21.02。
- 厂商定制固件、ImmortalWrt、iStoreOS 等派生版本必须按实际内核、包管理器、fw3/fw4、LuCI 和 openNDS 版本逐台验证，不能仅根据版本号推断兼容。

### 11.2 IPK / APK 交付格式

MT6000 原厂固件具体是否使用 opkg 需实机确认，使用 opkg 时交付 `.ipk`；OpenWrt 25.12 使用 apk 包管理器，实际构建/分发包格式应按 25.12 SDK 和包构建系统生成（通常为 `.apk`）。Agent 必须分别确认目标平台的 package format，不要把 25.12 的包强行改名为 `.ipk`。

### 11.3 资源要求

报价单写明最低内存 128MB。该值只能作为初步门槛，最终需要在指定设备上测试 openNDS、SQLite、LuCI 和 nftables 同时运行的内存占用、CPU 占用、闪存余量及吞吐量。若设备为极低闪存/内存型号，应重新评估功能和依赖。

## 12. 安全要求

1. 密码必须哈希存储，禁止明文、可逆加密或写入日志。
2. 登录接口增加基本的失败次数限制/短时冷却，避免无节制密码猜测。
3. 认证页与管理页隔离；普通账号不能调用管理 RPC。
4. 所有 RPC 使用最小权限 ACL；禁止任意 shell 命令执行、任意路径读写。
5. shell/CLI 调用必须固定命令和参数结构，所有外部输入严格校验，避免命令注入。
6. nftables 规则只能操作自有 table/chain/set/quota；不要 flush 系统全局规则。
7. 账号删除/额度变更/认证放行等跨组件操作需有失败补偿和日志。
8. 数据库文件权限只允许 root/服务必要身份读取。
9. FAS Token/共享密钥不得进入普通日志；认证回调对输入长度和格式做校验。
10. 无可信时间时暂停月度周期自动切换，避免时间错误造成额度提前恢复。
11. 后端异常时认证默认 fail-closed：不能因为 NetQuota 服务挂掉就让未认证用户直接联网。
12. 路由器管理网络必须可维护；不允许把管理面误纳入普通用户流量封锁规则。

## 18. GL-MT6000 原厂固件适配（P0 / 必须先完成）

### 18.1 确认具体固件，而非根据芯片名称猜测

目标设备：**GL.iNet GL-MT6000（Flint 2），原厂 GL.iNet 4.x 固件优先**。启动开发前由 Agent 在客户机器只读采集：`cat /etc/openwrt_release`、`ubus call system board`、`uname -a`、`opkg --version`、`iptables -V`、`nft --version`、`uci -q show firewall`、`uci -q show mtkhnat`、`lsmod | grep -Ei 'hnat|warp|wed|mt_wifi|mt76|ppe'`、`ip -br link`、`df -h`、`free -m`、`ubus list`。部分命令不存在属正常，应标注“不可用”，不能自动装包改变客户环境。

必须记录精确固件 build、kernel ABI、LuCI/rpcd 版本、fw3/fw4、无线驱动/转发路径、加速选项、DPI/Data Statistics/SQM 是否启用、WAN 和 Guest Network 拓扑。`luci-app-netquota` 和 `netquota` 可按这个 ABI 构建，首发不要宣称与所有 GL 4.x 版本通用。

### 18.2 关闭加速只是前提，不能当作已经完成验证

GL.iNet 官方在 Network Acceleration 文档明确说明：开启加速时客户端流量统计与限速可能工作不正常；GL-MT6000（Flint 2）在支持列表。官方 Data Statistics 文档说明固件 v4.9 起提供该功能，和 Network Acceleration 互斥，且某些来自隧道接口的流量不被它纳入统计。

本项目不能将 GL 原厂 Data Statistics 的**设备级**数据直接代替 NetQuota 的**账号级**流量账本，也不能只关闭界面开关就断言硬件 HNAT/WED 已完全绕开。需要实机测量独立计数点与转发控制链的可见性。与厂商已有 DPI/QoS/SQM/加速规则冲突时须降级提示，并提交兼容结果，不允许静默破坏原厂功能。

### 18.3 计量与阻断引擎应有可替换适配层

- `TrafficBackend` 抽象：`probe()`、`attach_session()`、`detach_session()`、`read_upload_download()`、`enforce_total_quota()`、`begin_period()`、`restore()`、`cleanup()`。
- 优先选择经实机证实可用的内核 netfilter / nftables 计数与拦截实现；如果不存在命名共享 quota 表达式，不能伪装成可用。可以评估另一种系统兼容实现，但必须证明“同账号多终端 + 上下行合计 + 到量阻断 + 持久恢复”。
- 方向定义：**上传**为受控用户终端发往 WAN 的转发字节，**下载**为 WAN 发往受控用户终端的转发字节；本地路由器管理面和同一 LAN 内横向流量不计入。对 NAT、IPv6、VPN、PPE/HNAT、flow offload、桥接路径逐项验证是否正确计量。
- 需防止同一报文在多个 hook 中重复累计；数据库保留上行、下行两个单调计数与同一逻辑总额度，并明确检查点的原子性。
- 必须验证客户端在配额耗尽后的**已建立连接**确实被切断，不是仅仅阻止新连接；断网策略不应影响路由器管理 LAN。
- 校验性能与计量精度。停用加速影响满速吞吐时须记录测试结果并向客户说明。不可保证“绝对 0 字节超额”，实际误差以验收报告为准。

### 18.4 兼容性门槛与 P0 实测用例

| ID | 实测项目 | 必须通过的条件 |
|---|---|---|
| M01 | 探测原厂 GL 固件与驱动栈 | 出具可核查版本与兼容性清单 |
| M02 | 加速开/关各做上传、下载大流量 | 记录准确性变化，找到可控/可计量的稳定路径 |
| M03 | 同账号两台设备并发上传/下载 | 四条方向计数汇入一个账号总配额，不超配 |
| M04 | 高速大文件传输接近额度 | 核查阻断延迟及最大超额；已建连接停止 |

## 19. 用户自助改密和账号级重置日（客户新增强制要求）

### 19.1 自助修改密码：独立用户权限域

- 普通用户从认证门户点击“我的账号 / 修改密码”进入自助页面；不是 LuCI 管理员页面，不给普通用户 rpcd 管理 ACL。
- 已认证用户需具备由服务端验证的会话身份，且更改密码时**必须输入原密码、新密码、确认新密码**。不得从客户端传入任意 `user_id` 并允许更新其他账号；身份始终从用户会话读取。
- 严禁仅凭 MAC/IP 认定用户身份；门户会话令牌随机且不可预测，Cookie 使用 `HttpOnly`、`SameSite`，在 HTTPS 下加 `Secure`；CSRF 防护、限流、过期退出、身份重新校验不可省略。
- 推荐 PBKDF2-HMAC-SHA256（按目标系统可用加密库选取足够成本参数）或 Argon2id；唯一 salt、后端哈希校验、常量时间比较、禁止明文密码和日志回显。正式密码最少 8 字符，实际安全策略和库依赖需实机验证。
- 修改成功后原密码立即不可再登录；现有其他会话的处理建议：**撤销该账号全部认证会话并要求重新登录**，同时不重置流量账本。页面必须明确告知可能断开当前网络。
- 即使额度已用尽，也应保持到 NetQuota 自助门户的受限网络访问（Walled Garden），完成改密不等于恢复上网权限；不能借门户访问任意互联网地址。
- 无受信任 TLS 的用户自助改密有密码泄露风险：**默认不能在明文 HTTP 上传输原密码/新密码**。必须先确定证书/本地 HTTPS/FAS 安全路径；不可用时界面提示未启用并交付风险评估，不得暗称安全。
- 管理员在 LuCI 修改某个用户密码属于另一权限域；用户自助改密不得暴露其他用户信息、管理 RPC、系统 shell 和账号列表。

### 19.2 账号级周期 API 与数据库行为

- `create_account` 输入：`username, password, quota_bytes, reset_day`；`reset_day` 可为 1–31 或 `null`（继承系统默认）。
- `update_account` 允许修改 `quota_bytes` 与 `reset_day`（后者排期至下个周期）；响应返回 `current_period`、`effective_reset_day`、`pending_reset_day`、`pending_effective_at`、`next_reset_at`。
- `get_settings / update_settings`：全局 `default_reset_day`、`timezone`（管理员权限）；变更需确认且不重置历史流量。
- `get_my_account`：仅返回本人的账号名、当前周期、有效重置日、已用 up/down、总配额/剩余、下次重置时间，不返回密码哈希或敏感系统信息。
- `change_my_password`：需要当前已认证用户会话 + 旧密码验证 + CSRF token；成功后修改密码哈希并处理会话撤销。
- 账号当前周期、待生效重置日与历史账本关联必须使用事务，确保服务重启或接近重置时刻并发修改不会多重结算。

### 19.3 追加验收用例

| ID | 验收场景 | 预期结果 |
|---|---|---|
| C01 | 系统默认 1 日，账号 A=15 日、B=25 日 | 两账号各自在其结算日 00:00 恢复，不互相影响 |
| C02 | 设置重置日=31，连续经过 2 月与 3 月 | 短月最后一天重置，3 月恢复 31 日锚点，无日期漂移 |
| C03 | 结算日前后跨期持续传输 | 上行、下行正确归属；不丢失/重复累加，不重复清零 |
| C04 | 修改账号重置日 15→20 | 当前周期账本不清零；从下一周期生效，显示明确时间 |
| C05 | 用户登录后使用旧密码改密 | 新密码有效、旧密码失效，其他账号不受影响 |
| C06 | 输入错误原密码、伪造 user_id、CSRF、爆破 | 改密被拒绝；不泄漏账号信息，存在限流告警 |
| C07 | 额度用尽的账号访问自助改密页面 | 可改密码但仍无法浏览互联网 |
| C08 | 上传 3GB、下载 7GB，额度 10GB | 上下行分别显示 3/7GB，总量10GB自动断网 |
| C09 | 两设备同时上/下行消耗同一额度 | 方向分别正确累加，合计只消耗账号共享 1 份额度 |
| C10 | 关闭浏览器、重启后台、路由器重启 | 自助账号状态与周期账本持久正确，配额保护恢复 |

### 19.4 对原报价范围的说明

原报价 A 明确包含账号管理、单账号月流量配额、基础流量展示、用尽自动断网和次月恢复；**本 V1.1 新增的可自定义结算日、用户自助密码修改、GL-MT6000 原厂专有转发适配均是明确的需求增量/环境适配工作**。它们应进入本次新版验收，但需要项目负责人与客户确认是否在既定金额/工期内完成。上传与下载分别统计且合并计入额度已在旧方案中约定，不另推导为“可设置每方向独立限额或独立限速”。
